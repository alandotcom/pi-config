# Recall

Read [the Pi execution contract](../../pi-runtime.md). Rebuild the user's working context from the current thread and its known artifacts. Pi's native recall is thread-scoped; this adaptation deliberately does not mine unrelated chats.

1. Classify the request. One named prior session routes to session pickup. Turning working habits into a skill routes to automate-me. If the user supplied a complete capsule, use it and verify current files.
2. Pin the topic and authorized history scope. Call the native `recall` tool before repeating investigation. Broader history requires an explicit user request and known accessible transcript paths. Report when that scope is unavailable instead of quietly narrowing it.
3. Reduce the retrieved evidence to goal, decisions, current branch, completed work, failed attempts, open questions, and artifacts. Fresh delegates cannot search the caller's thread. Supply selected excerpts if parallel synthesis is useful.
4. When a named feature or subsystem needs shared-record evidence, use the why reference to query the available source categories. Keep those queries read-only and report gaps.
5. Verify surfaced branches, PRs, tickets, and files against current state. Treat agent summaries as evidence to check rather than completed work to assume.
6. Write a tight capsule, one status-tagged line per thread, the important recurring problems, and the next concrete action. Use real citations and sanitize private context before public output.

Status tags include `[merged #N]`, `[open PR #N]`, `[in flight <branch>]`, `[verified, uncommitted]`, `[reverted #N]`, and `[planned, not started]`. Include only tags supported by evidence. Use the unslop reference for the reply.
